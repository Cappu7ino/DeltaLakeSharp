# API Ergonomics For Agentic Coding

This file captures API surfaces that are powerful but easy for agents or new consumers to misuse.

## Default Constructor Biases Toward V1

Current shape:

- `new DeltaTableServiceClient(Uri serverUri)` selects `ServiceMode.V1_Spark`.
- `new DeltaTableServiceClient(ServiceMode.V3_Rust)` selects the preferred in-process SDK runtime.

Risk:

- Agents may copy the URI constructor even when the consumer wants the package-native V3 path.

Recommendation:

- Add named factories or documentation examples that make intent explicit, such as `CreateNative()` and `CreateFlight(Uri, ServiceMode)`.
- Keep AI docs explicit that V3 is preferred for new external NuGet integrations.

## One Client Type Hides Capability Differences

Current shape:

- `DeltaTableServiceClient` exposes one API surface over V1, V2, and V3.
- Some methods throw `NotSupportedException` on V1/V2.

Risk:

- Agents may select APIs without checking backend capability.

Recommendation:

- Add a public capability descriptor or helper in the future, for example `client.Capabilities.SupportsChangeDataFeed`.
- Keep capability matrices near all integration guidance.

## Native Runtime Discovery Is Implicit

Current shape:

- V3 loads `delta_table_service_native` from runtime-specific or development paths.
- Failure surfaces as native loading or operation exceptions.

Risk:

- Consumers may not know which runtime asset is missing or where the package expects it.

Recommendation:

- Add a diagnostic helper that reports native library resolution candidates and the selected path.
- Document packaging expectations in every V3 setup guide.

## Storage Option Overloads Are Easy To Mix

Current shape:

- Many methods accept both `StorageConfig?` and `GenericStorageOptions?`.
- `StorageConfig` is legacy typed SAS/account configuration; `GenericStorageOptions` is dictionary pass-through.

Risk:

- Agents may pass both without explaining precedence or backend relevance.

Recommendation:

- Consider a unified request options object for new APIs.
- Prefer one documented storage option path per guide.

## SQL DML Is String-Based

Current shape:

- `DeleteAsync`, `UpdateAsync`, and `MergeAsync` accept SQL strings and validate operation prefixes.
- `MergeDataAsync` uses structured `MergeOptions` for streaming source data.

Risk:

- Agents may generate syntactically valid strings for the wrong helper or backend.

Recommendation:

- Prefer structured APIs where possible.
- Add examples that distinguish SQL MERGE from streaming `MergeDataAsync`.

## Partition Tokens Are Public But Opaque

Current shape:

- `DeltaReadPartition` exposes token and metadata.
- Read APIs accept either a partition descriptor or token string.

Risk:

- Agents may construct or persist tokens manually.

Recommendation:

- Emphasize that tokens are generated by `GetReadPartitionsAsync` and are not stable long-term IDs.
- Consider hiding construction or adding stronger factory semantics in future API revisions.

## ADBC Single-Table Scope Can Surprise Users

Current shape:

- ADBC exposes one path-scoped logical table, commonly `delta_table`.
- Real catalog discovery, writes, transactions, and prepared statements are out of scope.

Risk:

- Agents may generate generic database-driver code that expects multi-table catalogs or write commands.

Recommendation:

- Keep ADBC docs read-only and path-scoped.
- Prefer `DeltaTableServiceClient` examples for mutations.

## Materialization Helpers Need Guardrails

Current shape:

- `ToDataTableAsync` and `ToListAsync` are convenient and discoverable.

Risk:

- Agents may choose them as defaults for large datasets.

Recommendation:

- Put streaming examples first.
- Show materialization only for bounded data, tests, and small administrative queries.
